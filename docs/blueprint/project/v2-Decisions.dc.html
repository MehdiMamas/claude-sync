ADR-001: Desktop shell

Status: accepted · 2026-11-26

Context. A tray utility that is open a few minutes a week and idle the rest. Budgets: 40 MB in the tray, 1 s cold start. Windows, macOS, Linux beta.

  • Chosen: Tauri 2 with a Rust core; the window is created on open and destroyed on close. Pros: System webview, small installer, Rust for the engine, first-party tray, single-instance and signed updater plugins. Cons: Webview differences across OSes need a Playwright run per OS.
  • Rejected: Electron. Why not: Ships Chromium and Node in every app: a far bigger baseline in memory and installer than the 40 MB tray budget.
  • Rejected: Wails (Go). Why not: Workable, but its tray and updater are not first-party in the same way; the second opinion favoured Tauri for exactly that.
  • Rejected: Flutter desktop. Why not: Dart and its own rendering stack: a smaller hiring pool for a settings utility and no gain for a form-heavy UI.

Sources: Tauri 2 architecture: system webview, Rust core · Electron process model: Chromium and Node per app · Wails v3 FAQ · Flutter desktop support · Stack Overflow Developer Survey 2025: technology

ADR-002: UI

Status: accepted · 2026-11-26

Context. About 105 screen states, mostly forms, lists and diffs. Must be easy to hire for and testable without the shell.

  • Chosen: React with strict TypeScript, Vite, Vitest + Testing Library, Playwright against a fake backend; CSS variables from the palette, no component library. Pros: Largest front-end pool; screens are pure functions of a snapshot; the fake backend keeps the ?state preview URLs. Cons: React runtime adds about 45 KB gzipped; still under the 200 KB budget.
  • Rejected: Vanilla TypeScript (as v1). Why not: Hand-made rendering and state for 76 states is the code that is hard to change today.
  • Rejected: Svelte. Why not: Smaller pool.
  • Rejected: Leptos or Yew (Rust UI). Why not: Very small pool, slow UI iteration.

Sources: Stack Overflow Developer Survey 2025: technology

ADR-003: Sync engine

Status: accepted · 2026-11-26

Context. Must cost nothing when idle, never lose a local edit, and survive a crash mid-sync.

  • Chosen: GitHub REST only: conditional GET of main per repo with the stored ETag, then tree and only changed blobs. A pure planner (remote + base + local gives a Plan) and an executor that writes temp files, renames, then commits the new base in one SQLite transaction. One tokio actor owns the engine; sync.lock shared with the CLI. Pros: A 304 is free; the planner is property-tested without network or disk; a crash leaves the old base, so the next tick redoes the plan. Cons: One request per repo per tick instead of one batched call: at the v1 default of 1 minute, 240 head GETs + 180 open-proposal GETs + 4 invitation GETs = 424 an hour at 3 groups + personal, all free 304s (88 at 5 minutes), plus one repo GET per repo a day for renames.
  • Rejected: GraphQL batch of heads (as v1). Why not: v1 added it (issue 144) when the REST quota, shared with other tools on the same login, hit 0 while polling without ETags on every call. GraphQL has no conditional requests and is a second code path; GitHub docs (REST best practices, fetched 2026-11-26): a 304 to an authorized conditional request does not count against the primary rate limit. The bench counts real points once against GitHub before the switch; if 304s are charged, the GraphQL batch comes back.
  • Rejected: libgit2 clones (git2). Why not: A large native dependency and full clones for a few small files.
  • Rejected: git CLI. Why not: Git for Windows is optional for Claude Code users, so it cannot be assumed.
  • Rejected: gix (pure Rust git). Why not: Still a clone per group for a handful of files; no gain over the API.

Sources: GitHub REST best practices: conditional requests, a 304 does not count against the primary limit · git2 (libgit2 bindings) · Claude Code setup: Git for Windows is optional

ADR-004: Local storage

Status: accepted · 2026-11-26

Context. v1 keeps about ten JSON files (state, manifest, jobs, notifications, requests...). Writes must be atomic together.

  • Chosen: SQLite through rusqlite (bundled), WAL mode, versioned migrations; a one-time importer reads the v1 JSON files and keeps them as a backup. choices.json stays in the personal repo so choices still follow the person. Pros: Atomic multi-table commits; one file; a schema the ER frame shows; testable in memory. Cons: A binary file is harder to read by hand: `claude-sync status --json` and `debug dump` cover that.
  • Rejected: JSON files (as v1). Why not: No transaction across files: a crash between two writes leaves them out of step.
  • Rejected: redb or sled. Why not: Smaller pools and no SQL to inspect the data.

Sources: SQLite atomic commit

ADR-005: Consent model (as v1)

Status: accepted · 2026-11-26

Context. Group content becomes Claude instructions, plugins and scheduled jobs on the member machine. v1: claude-sync.json autoAcceptClaudeMd (default true), each person's Follow group / Review first / Auto-accept, a yes per job, and plugins, skills, agents and shared settings applied without a per-item yes.

  • Chosen: Keep v1 exactly. CLAUDE.md: the host setting autoAcceptClaudeMd (default on) decides, and each person's choice overrides it on all their machines. Jobs: a yes per job (or the per-device job auto-accept, as v1), shown with prompt, folder, permission mode (bypassPermissions warned) and args. Plugins, skills, agents and shared settings apply on sync without a per-item yes; that is why Join and invitations show the plugins warning, every share is secret-scanned and plugin files are capped at 1 MiB. Pros: Parity with v1; groups exist to deliver these automatically. Cons: A member trusts the group at join time; the warning says so.
  • Rejected: A yes for every item, default off. Why not: Changes v1 behaviour (default on) and makes every plugin update a click; groups stop working on their own.
  • Rejected: Trust the host for jobs too. Why not: A job runs Claude on the member machine; one compromised host account would reach every member.

ADR-006: Personal memory home

Status: accepted · 2026-11-26

Context. Personal files must never travel through a group.

  • Chosen: A private repo of the user own named claude-sync-personal, marked by claude-sync-personal.json (as v1, personal.rs), visibility checked every pass. Pros: No extra account or server; v1 and v2 machines share the same repo. Cons: Needs a GitHub repo per user.
  • Rejected: A cloud drive. Why not: Another account and client to install.

ADR-007: Sign-in and token scope

Status: accepted · 2026-11-26

Context. A desktop app with no server for redirects; the CLI must use the same flow. Group and personal repos are private.

  • Chosen: OAuth device flow with a public client id and scopes repo and read:user (as v1); token in the system keychain (CLI: ~/.claude-sync/token, mode 0600). The GitHub App mode (beta) stays opt-in, with 8-hour tokens, refresh and per-repo access; Manage app access opens GitHub. App mode becomes the default only after a release where it passes every Parity row (see Questions 4). Pros: repo is the only OAuth scope that reads private repos; no secret in the app; works headless. Cons: repo is wide: it reaches every repo of the user. The App mode is the narrow path for those who want it.
  • Rejected: GitHub App as the default now. Why not: Each member must install the app on every group repo, and invitations, transfer and personal-repo creation need extra permissions; v1 never proved that path end to end.
  • Rejected: Local redirect server. Why not: Free port and firewall prompt.
  • Rejected: Pasted personal access token. Why not: Long-lived, wide secret in a text box.

ADR-008: Updater

Status: accepted · 2026-11-26

Context. Releases of MehdiMamas/claude-sync are public. v1 asks the relay, which proxies GitHub with a token and a 120-an-hour limit.

  • Chosen: Tauri updater plugin reading a static latest.json asset from the latest GitHub Release; minisign signature checked with the key in the app. Pros: No server, no token, no rate limit of ours; the plugin supports a static JSON endpoint. Cons: Release notes must be written into latest.json at release time (release.yml step). Key custody: the minisign private key is the TAURI_SIGNING_PRIVATE_KEY secret (plus password) with an offline copy in the owner password manager; if it is lost, installed apps reject new updates and each user reinstalls once from the Releases page. v2 signs with the same minisign key as v1 and keeps the v1 asset names, so v1 installs update to v2 through the relay (Cutover frame).
  • Rejected: Relay /api/update for v2 too. Why not: A server and a token for a file GitHub already serves publicly; kept only for v1 clients until retirement.
  • Rejected: Sparkle or WinSparkle. Why not: One updater per OS instead of one.
  • Rejected: App stores. Why not: Review delays and store fees for a small group tool.

Sources: Tauri updater plugin: static JSON endpoint, signature required

ADR-009: Relay

Status: accepted · 2026-11-26

Context. Private feedback attachments need a secret that must not ship in the app.

  • Chosen: Keep one Vercel function: POST /api/feedback (issue filed with the user own token, attachments to a private repo) and GET /api/health. The relay keeps v1 feedback behaviour: required kind (bug or idea) and title, labels feedback and type:<kind>, the nearest open sprint milestone, the per-user rate limit, 403/422/413/429 answers. The triage bot (relay/triage) stays as it is: it runs on a machine by launchd, not on Vercel. Kept unchanged for v1 clients until v1 is retired: /api/update and /api/download (v1 has no other update path, updates.rs:104). /api/install becomes a redirect to the Releases page, because group READMEs in the field link it (group.rs:25). Removed at retirement (Cutover frame). Pros: Already deployed and free on Hobby; smallest possible surface. Cons: Hobby is for non-commercial use: fine for this free tool, re-check if that changes.
  • Rejected: Move to Cloudflare Workers. Why not: A migration with no gain at this volume.
  • Rejected: No relay, attachments in the public issue. Why not: Screenshots and logs would be public.
  • Rejected: The app files the issue itself; the relay takes attachments only. Why not: The relay would then need another way to tie an upload to a real user; checking the token once on the relay is simpler, and the relay never stores it.

Sources: Cloudflare Workers pricing · Vercel Hobby plan

ADR-010: Command line

Status: accepted · 2026-11-26

Context. v1 has two CLIs: the app binary (status, personal) and claude-sync-cli (everything, headless).

  • Chosen: One clap command tree compiled into both binaries, which keep their v1 names: the desktop app `claude-sync` (identifier com.mehdimamas.claudesync, GUI subsystem on Windows) and the headless `claude-sync-cli` (console program; on Windows it prints without piping); the app binary keeps the hidden `run-job` and `remove-jobs` (the NSIS pre-uninstall hook runs it, skipped on update) (GUI subsystem on Windows, so no console flash) and `--background`, `--refresh`; the headless CLI keeps `run-job` too, for servers and WSL (as v1, crates/cli/src/main.rs). Pros: One command set to document and test; OS tasks, autostart entries, the NSIS uninstall hook, the ~/.local/bin/claude-sync link, systemd and cron lines and relay asset names that v1 wrote keep working with no migration. Cons: Two binaries to ship (as now).
  • Rejected: Keep both CLIs. Why not: Two command sets that drift.
  • Rejected: Rename to claude-sync (console CLI) and claude-sync-app (GUI). Why not: Breaks every v1 OS task, autostart entry, uninstall hook, CLI link and service line (app/src-tauri/src/jobs.rs:37, crates/cli/src/jobs.rs:19, windows/hooks.nsh, cli.rs:283, crates/cli/src/service.rs); each would need migration code. The GUI exe keeps the Out-String pipe of issue 149.
