update.ts · cache, order, answer
The release cache is one global entry per function instance (not per repo): {etag, release, at}. A stale answer served after a 403/429 does not refresh `at`, so every later request retries GitHub until it answers. A cached ETag is sent as If-None-Match; no ETag header on the answer means no conditional request next time. A 304 with nothing cached cannot happen because no etag is sent then.cacheupdate.ts:20-25,38-63
Other failures (500, 401, 403 with nothing cached) give 502 "GitHub latest release returned <n>".cacheupdate.ts:20-25,38-63
Validation order: caller check, target, arch, current_version, then env (RELEASES_REPO, RELAY_GITHUB_TOKEN). Parameter values are case-sensitive; a missing parameter gives the same message as a wrong one. current_version is trimmed and may have a leading v, build metadata and a prerelease; empty gives 400 "current_version must be a semver version".orderupdate.ts:91-101
Answers: the latest release is whatever GitHub's /releases/latest returns (GitHub itself skips prereleases and drafts there; the relay only re-checks the draft flag). The version sent back is the tag normalised without v and without build metadata (formatSemver); asset names use that same version. Every 200 and 204 carries cache-control: no-store and nothing else (no Vary, no ETag).answerupdate.ts:102-117

attachments.ts · order, commit
No files -> nothing. GET repo default_branch; blobs POSTed once each (base64), tree entries mode 100644 type blob. Up to 3 attempts of: GET git/ref/heads/<branch> (segments path-encoded), GET git/commits/<sha>, POST git/trees with base_tree, POST git/commits with parents [head], PATCH git/refs/heads/<branch> {sha}. A 422 on the ref update retries on the new head; other status or 3rd failure throws 502 `GitHub update attachments ref returned <n>`. Error labels: attachments repo, attachment blob, attachments ref, attachments commit, attachments tree.orderattachments.ts:1-56
commitFiles uploads blobs one after another (a later failure leaves unused blobs, which GitHub drops), then loops: read the branch head, read its commit, create a tree on it, create a commit with that single parent, PATCH the ref without force. Commits go straight to the default branch of the attachments repo under the token owner's name.commitattachments.ts:20-55
An empty repo has no ref and gives 502 "GitHub attachments ref returned 404", caught by the caller so the issue says the files could not be stored.commitattachments.ts:20-55
