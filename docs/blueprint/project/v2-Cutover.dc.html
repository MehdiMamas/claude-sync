Cutover from v1

Created 2026-11-26. Updated 2026-11-26.

Every v1 install in the field must reach v2 by itself, and nothing a v1 machine wrote may break.

How v1 installs reach v2

  • v1 has no updater endpoint of its own (tauri.conf.json endpoints: []); it asks the relay /api/update with the user token (app/src-tauri/src/updates.rs:104; the CLI: crates/cli/src/update.rs:83). Those routes stay unchanged until v1 is retired.
  • v2 releases keep the v1 asset names (claude-sync_<version>_<os>_<arch> plus .sig, matched by relay/lib/assets.ts:22-24; claude-sync-cli-<triple>.tar.gz or .zip plus .sha256 holding a binary named claude-sync-cli) and the same minisign key, or v1 sees no update.
  • The relay /install page becomes a redirect to the Releases page: group READMEs already in the field link it (crates/core/src/group.rs:25).
  • Tags stay v<semver> and v2 ships as 2.0.0, above v1 0.1.x (the relay ignores tags that are not semver, update.ts:106); installers keep their v1 names (claude-sync_<version>_windows_x86_64-setup.exe, claude-sync_<version>_darwin_universal.dmg), so README.md and scripts/install-cli.sh need no change.
  • aarch64 Linux has no desktop build (v1 never made one), so the relay finds no app bundle there and answers 204 (update.ts:111-118). Chosen: the relay, for target=linux and arch=aarch64 only, answers {version, url: claude-sync-cli-aarch64-unknown-linux-gnu.tar.gz, signature: ""} when that archive and its .sha256 are in the release. The v1 CLI reads only version, then downloads the archive and .sha256 itself (update.rs:42-54, 112-118); no Tauri updater runs on that target. Rejected: building an aarch64 GUI AppImage only to satisfy the relay (a build nobody runs).
  • Signed-out or expired v1 installs cannot ask the relay (the check sends the token). They see v2 once signed in again; the README and the Releases page say so.
  • Release assets, every release (relay/lib/assets.ts, release.yml): claude-sync_<v>_windows_x86_64-setup.exe and .sig; claude-sync_<v>_darwin_universal.app.tar.gz and .sig; claude-sync_<v>_darwin_universal.dmg; claude-sync_<v>_linux_x86_64.AppImage and .sig; claude-sync_<v>_linux_x86_64.deb; claude-sync-cli-x86_64-unknown-linux-gnu.tar.gz, claude-sync-cli-aarch64-unknown-linux-gnu.tar.gz, claude-sync-cli-aarch64-apple-darwin.tar.gz, claude-sync-cli-x86_64-apple-darwin.tar.gz and claude-sync-cli-x86_64-pc-windows-msvc.zip, each with .sha256; new in v2: latest.json.
  • latest.json platforms: windows-x86_64 (setup.exe), darwin-aarch64 and darwin-x86_64 (both the universal .app.tar.gz), linux-x86_64 (AppImage), each {url, signature} taken from the .sig. No linux-aarch64 entry: the v2 CLI there reads version from latest.json and fetches its archive and .sha256.
  • Rollout: the v2 release is first published as a pre-release (not releases/latest, so the relay does not serve it), tried on the owner machines, then marked latest. Removing the latest flag stops new updates.

What stays the same on the machine

  • Binary names and identifier: claude-sync (app, com.mehdimamas.claudesync) and claude-sync-cli (ADR-010), so OS tasks, autostart, the uninstall hook, the CLI link and service lines keep working.
  • The ~/.claude-sync folder and the group files in it, at the same paths: CLAUDE.md imports them. store.db is added beside them.
  • Keychain service claude-sync, account @current plus one per login; v2 reads both the bare-token and the JSON token layouts (github.rs:205-212) with the same OAuth client id.
  • Task names (dev.claude-sync.job.<id>, Windows folder \claude-sync\); first start runs a verifying reconcile, so a moved exe re-registers and no job runs twice.
  • v1 daemon hand-over, done by v2 (there is no extra v1 release: installs on 0.1.27 or older jump straight to 2.0.0, and v1 update never stops its daemon). A v1 daemon keeps running old code after its exe is swapped and holds daemon.lock for its whole run (daemon.rs:112-126). Every v2 start (app, daemon, any CLI command) tries daemon.lock; v2 daemons write daemon.owner (pid, version), so a held lock with no live v2 owner is a v1 daemon. v2 finds it (same user, command line claude-sync-cli daemon), sends SIGTERM and polls the lock once a second for at most 30 s.
  • Freed: import_v1 runs; if a systemd unit is installed v2 runs systemctl --user restart claude-sync, because a SIGTERM exit is clean and Restart=on-failure (service.rs:45) would not restart it; with cron the 5-minute check starts the v2 daemon. Not freed in 30 s: nothing is imported or written; the app shows InstallV1Daemon, the CLI exits 1 with the pid and the stop command, and status says the same. Until then the v1 daemon writes only v1 files, so the two never write the same state.
  • Uninstall: v2 keeps the hidden remove-jobs on the app binary (Parity 42), run by NSIS_HOOK_PREUNINSTALL in app/src-tauri/windows/hooks.nsh (tauri.conf.json bundle.windows.nsis.installerHooks) and skipped when $UpdateMode is 1, so no task is left pointing at a deleted exe. Windows stays an NSIS currentUser install in the same folder.

Retiring v1

  • Counter: Vercel runtime logs cannot hold it (Hobby keeps 1 hour of logs, vercel.com/docs/logs/runtime, checked 2026-11-26). It lives in one Upstash Redis free database added through the Vercel Marketplace ($0: 500K commands and 250 MB a month, upstash.com/pricing/redis, checked 2026-11-26). Each /api/update with current_version below 2.0.0 does HINCRBY v1checks:<UTC date> <version> 1 and EXPIRE 90 days; if Redis is down the check is still answered. No token, login or IP is stored.
  • The owner reads it at GET /api/v1-checks (owner login only, checked with GitHub like feedback): per day, per v1 version, the last 90 days. The owner decides: when it shows 30 days in a row at zero, a Decisions card proposes removing /api/update and /api/download (Parity 52, 66, 68), and they go only after the owner yes.
  • Downgrade: one-way; the v1 files stay untouched as the manual way back (Questions 7).
