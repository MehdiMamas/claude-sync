Cutover from v1

Created 2026-11-26. Updated 2026-11-26.

Every v1 install in the field must reach v2 by itself, and nothing a v1 machine wrote may break.

How v1 installs reach v2

  • v1 has no updater endpoint of its own (tauri.conf.json endpoints: []); it asks the relay /api/update with the user token (app/src-tauri/src/updates.rs:104; the CLI: crates/cli/src/update.rs:83). Those routes stay unchanged until v1 is retired.
  • v2 releases keep the v1 asset names (claude-sync_<version>_<os>_<arch> plus .sig, matched by relay/lib/assets.ts:22-24; claude-sync-cli-<triple>.tar.gz or .zip plus .sha256 holding a binary named claude-sync-cli) and the same minisign key, or v1 sees no update.
  • The relay /install page becomes a redirect to the Releases page: group READMEs already in the field link it (crates/core/src/group.rs:25).
  • Tags stay v<semver> and v2 ships as 2.0.0, above v1 0.1.x (the relay ignores tags that are not semver, update.ts:106); installers keep their v1 names (claude-sync_<version>_windows_x86_64-setup.exe, claude-sync_<version>_darwin_universal.dmg), so README.md and scripts/install-cli.sh need no change.
  • aarch64 Linux CLI-only installs: the relay answers only when an app bundle with .sig exists for the target (update.ts:111-118), and v1 builds the AppImage for x86_64 only. release.yml adds an aarch64 Linux AppImage and .sig on the GitHub arm64 runner, so those servers see v2.
  • Signed-out or expired v1 installs cannot ask the relay (the check sends the token). They see v2 once signed in again; the README and the Releases page say so.
  • Rollout: the v2 release is first published as a pre-release (not releases/latest, so the relay does not serve it), tried on the owner machines, then marked latest. Removing the latest flag stops new updates.

What stays the same on the machine

  • Binary names and identifier: claude-sync (app, com.mehdimamas.claudesync) and claude-sync-cli (ADR-010), so OS tasks, autostart, the uninstall hook, the CLI link and service lines keep working.
  • The ~/.claude-sync folder and the group files in it, at the same paths: CLAUDE.md imports them. store.db is added beside them.
  • Keychain service claude-sync, account @current plus one per login; v2 reads both the bare-token and the JSON token layouts (github.rs:205-212) with the same OAuth client id.
  • Task names (dev.claude-sync.job.<id>, Windows folder \claude-sync\); first start runs a verifying reconcile, so a moved exe re-registers and no job runs twice.
  • A v1 daemon keeps running old code after its exe is swapped, and holds sync.lock only during a pass. The last v1 release (0.1.x) makes update stop its daemon after the swap, so systemd or the cron check restarts it on the new binary; import_v1 waits while daemon.lock is held, and v2 honours sync.lock and daemon.lock as v1 does.
  • Uninstall: v2 keeps the hidden remove-jobs, which the NSIS pre-uninstall hook runs (skipped on update), so no task is left pointing at a deleted exe. Windows stays an NSIS currentUser install in the same folder.

Retiring v1

  • The relay counts update checks per current_version per day (a log line per check, read from the Vercel runtime logs; a relay change in the Plan). When no v1 version has checked in for 30 days, /api/update and /api/download are removed (Parity 52, 66, 68).
  • Downgrade: one-way; the v1 files stay untouched as the manual way back (Questions 7).
